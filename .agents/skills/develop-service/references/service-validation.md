## Bean Validation

- **JAVA-VALIDATION-CONTRACT-001** **[DEFAULT][TOPIC]** — Prefer declaring public API method-parameter and return-value constraints on the API interface or API data type.
- **JAVA-VALIDATION-CONTRACT-002** **[REQUIRED][TOPIC]** — Declare parameter constraints and parameter cascade markers of inherited or implemented methods on the supertype contract; subtypes must not add, redeclare, or strengthen them. This prohibition does not apply to return-value constraints.
- **JAVA-MVC-OBJECT-VALIDATION-001** **[REQUIRED][TOPIC]** — For Spring MVC request-object validation at argument binding, use parameter-level @Valid for the default group or @Validated(Groups.class) for selected groups; never stack them indiscriminately. This choice does not apply to ordinary Bean method validation.
- **JAVA-MVC-METHOD-VALIDATION-001** **[REQUIRED][TOPIC]** — Use MVC built-in method validation for directly declared parameter or return-value constraints, with @Valid for nested object constraints. Controllers using this mechanism must not have class-level @Validated.
- **JAVA-VALIDATION-SPRING-BEAN-001** **[REQUIRED][TOPIC]** — For method-parameter or return-value validation on a regular Spring Bean such as a Facade or application service, put `@Validated` on the concrete Bean implementation and invoke it through the Spring proxy; the interface declares contract constraints and the implementation enables runtime method validation.
- **JAVA-METHOD-VALIDATION-GROUP-001** **[REQUIRED][TOPIC]** — For method-validation groups, ordinary Beans declare @Validated(Groups.class) on the implementation class or method, with method groups overriding class groups; MVC built-in method validation declares groups on the handler method. Object parameters or returns needing cascading still use @Valid; parameter-level @Validated does not replace a cascade marker.

## Explicit checks

- **JAVA-VALIDATION-REQUIRE-001** **[REQUIRED][TOPIC]** — Business-contract failures must throw the corresponding business exception with a stable business error code; never replace it with generic FrameworkException plus business prose. The business-exception base-type contract is defined in Exceptions and logging.
- **JAVA-REQUIRE-VALID-PURITY-001** **[REQUIRED][TOPIC]** — Require.satisfies predicates must be side-effect-free and depend only on the current value, immutable static final constants, class literals, and immutable values derived solely from the current value. Never capture other variables, parameters, instance fields, or mutable external state. A null value fails without predicate evaluation.
- **JAVA-REQUIRE-STATE-001** **[REQUIRED][TOPIC]** — Use Require.state only for a simple technical execution-state invariant. Its default string-message overload throws FrameworkException with ILLEGAL_STATE; its supplier overload accepts only FrameworkException subtypes so it cannot emit a business exception. Domain or use-case state violations remain explicit business guards.
- **JAVA-CROSS-VARIABLE-GUARD-001** **[REQUIRED][TOPIC]** — Use explicit guards for cross-variable checks or decisions depending on external state; never disguise them as Require.satisfies calls. Classify failures under the common failure-semantics rule.
- **JAVA-REQUIRE-NONNULL-SCOPE-001** **[REQUIRED][TOPIC]** — Use Require.notNull with a business-exception supplier for business nullability guards, not ordinary technical defense. Applicability of a business guard does not depend on whether it checks a parameter, return value, local variable, or field.
- **JAVA-REQUIRE-COLLECTION-CONTRACT-001** **[REQUIRED][TOPIC]** — Choose collection checks by their distinct contracts: notEmpty rejects null or empty containers but does not check elements; noNulls rejects null containers and null elements or Map keys/values but allows empty containers. noDuplicates also rejects duplicate elements; its keyMapper variant additionally rejects null or duplicate mapped keys. Both uniqueness variants allow empty input and return mutable Set/Map results, not immutable defensive copies; notEmpty and noNulls return the original container. Exception suppliers cover each method's structural check failures, not callback exceptions.
- **JAVA-COLLECTION-NULL-EXCEPTION-001** **[REQUIRED][TOPIC]** — Technical null-element checks cover collection elements and both Map keys and values and use semantics-matching technical exceptions; they do not replace business validity checks.
- **JAVA-REQUIRE-COLLECTION-BUSINESS-GUARD-001** **[DEFAULT][TOPIC]** — In modules depending on framework-kernel, prefer Require.noNulls with a business-exception supplier when non-null elements or Map keys/values are a business contract; enforce additional business constraints separately.
- **JAVA-COLLECTION-DUPLICATE-REJECTION-001** **[REQUIRED][TOPIC]** — When a business contract rejects duplicates, explicitly check uniqueness; never substitute silent deduplication through Set conversion.
- **JAVA-VALIDATION-CALLBACK-EXCEPTION-001** **[REQUIRED][TOPIC]** — Exception suppliers do not translate exceptions thrown by callbacks. Exceptions thrown by Require predicates or keyMapper and NullSafe consumers propagate unchanged.
- **JAVA-NULLSAFE-COPY-SELECTION-001** **[DEFAULT][TOPIC]** — In modules already depending on framework-core, prefer NullSafe.copyTo* for immutable shallow copies only when the NullSafe input contract and exception semantics fit. Use copyToOrdered* when input iteration order must be preserved. Built-in null-element checks need no repeated Require.noNulls; Set copies deduplicate.
- **JAVA-NULLSAFE-EXCEPTION-SCOPE-001** **[REQUIRED][TOPIC]** — NullSafe exception suppliers handle only null elements or null Map keys/values, not null containers. Business element checks require a business-exception supplier; default technical exceptions are appropriate only when the contract accepts framework error codes.
- **JAVA-NULLSAFE-CALLBACK-CONTRACT-001** **[REQUIRED][TOPIC]** — NullSafe.visit requires a non-null consumer and checks it even when the container is null; copy methods allow an omitted consumer. A null container skips visit or becomes an empty copy without invoking the element exception supplier.
- **JAVA-CONTAINER-NULL-SEMANTICS-001** **[REQUIRED][TOPIC]** — Use NullSafe.visit or copyTo* only when input null and empty containers are both allowed and semantically equivalent. Traverse or copy guaranteed non-null inputs directly; do not precheck non-nullness and then use NullSafe.
- **JAVA-CONSTRUCTOR-CONTAINER-NULLABILITY-001** **[REQUIRED][TOPIC]** — Constructor collection and Map parameters are non-null by default; allowing an empty container does not imply allowing null. Document each nullable parameter in the constructor Javadoc @param with its null-handling semantics and any conditions under which null is permitted. Never implicitly widen null acceptance by using NullSafe.
- **JAVA-VALIDATION-API-001** **[DEFAULT][TOPIC]** — Prefer Jakarta Bean Validation for API field-shape constraints; a check returns a business error only when the API contract explicitly promises that error semantics. Execute the check at its responsibility boundary rather than moving it into API or protocol code because the API exposes the error.
- **JAVA-VALIDATION-LAYER-001** **[REQUIRED][TOPIC]** — Validate rules that depend on domain state, persistence data, or use-case context in application or domain rather than moving them to the protocol-binding layer.

## Exceptions and logging

- **JAVA-BEAN-VALIDATION-EXCEPTION-001** **[REQUIRED][TOPIC]** — At the unified boundary classify validation failures by source: external input violating public constraints yields the promised input-validation error; return-contract violations, invalid constraint declarations, and validator configuration failures are server defects, not caller input errors or expected business rejections. A unified error contract does not require catching and rethrowing framework exceptions before rendering the response.
- **JAVA-BUSINESS-EXCEPTION-BASE-001** **[REQUIRED][TOPIC]** — Service-defined DomainException, ApplicationException, and InfrastructureException extend framework-kernel `BaseException`, never JDK RuntimeException or other JDK exceptions directly.
- **JAVA-DOMAIN-GUARD-001** **[REQUIRED][TOPIC]** — Guards expressing domain rules or domain validity throw the corresponding domain's DomainException, not generic IllegalArgumentException or IllegalStateException. Programming errors and technical preconditions inside domain remain technical exceptions.
- **JAVA-DOMAIN-EXCEPTION-FACTORY-001** **[REQUIRED][TOPIC]** — Each domain's `DomainException` provides `invalidEntityId()` for invalid domain entity identifiers. The error-code policy exclusively defines the code allocation for `DOMAIN_ENTITY_ID_INVALID`.
